# Adding objects to the twin

This folder explains how to add objects to the scanned room, such as a fire extinguisher, a cabinet, or the real
position of an asset, and how they reach the 3D page, the assistant and the data layer. Drop a JSON file into
`data/objects/`, check it, rebuild, and the object appears. You never edit the generated files.

## Quick start

1. Copy an example from [examples/](examples/) into `data/objects/`, for example `data/objects/fire_extinguishers.json`.
2. Set the `id`, the `class` and the `box` (see [Finding coordinates](#finding-coordinates)).
3. Check it:
   ```bash
   python pipeline/added_objects.py
   ```
4. Rebuild the scene, then the data layer. Both need the scan and the builder pack, which are not in the repo:
   ```bash
   SKIP_SPLAT=1 python pipeline/build_scene.py "Equipment Room.ply" builder_pack.xlsx data/semantic_layer.json web
   python pipeline/build_layer.py builder_pack.xlsx
   ```
   If you do not have them, commit your object file after step 3, and whoever has the scan runs step 4.
5. Start the app (`python -m backend --gpu`) and reload the page.

## The object format

A file holds one object, a list of objects, or `{"objects": [...]}`.

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Unique name, 1 to 40 letters, digits, `_` or `-`. Must not match an existing object. |
| `class` | yes | What it is, in plain words: `"fire extinguisher"`, `"electrical cabinet"`. Stored in lower case. |
| `box` | yes | Either `{"center": [x, y, z], "size": [sx, sy, sz]}` or `{"min": [x, y, z], "max": [x, y, z]}`. |
| `tag` | no | An asset tag from the builder pack, such as `"M-002"`, when this object is that asset. |
| `class_confidence` | no | `"high"`, `"medium"` (default) or `"low"`: how sure you are about the class. |
| `source` | no | Who found it: `"manual"` (default), `"vision model"`, or a tool name. |
| `note` | no | Anything that helps the next person: what you saw and where. |

Any other field is refused, so a misspelled field cannot slip through.

## Finding coordinates

All coordinates are in the raw scan frame, in scan units, which are close to but not exactly metres.

- **x and z** are the floor directions. The room runs about -4.7 to 4.1 in x and -3.6 to 3.4 in z.
- **y points down.** The floor is at y ≈ 1.167, and a larger y is lower.
- An object standing on the floor with height `h` has `center y = 1.167 - h / 2`, so a 0.6-tall extinguisher has
  center y 0.867.

To read a position in the page, press **XYZ**. The panel shows:
- **walker:** where the walker stands. **Copy** puts it on the clipboard.
- **cursor:** the floor point under the mouse, and whether it is walkable.
- **floor y:** the floor height.
- **go to:** type x and z, then **Teleport** to check a spot.

With XYZ on, each Nearby card also shows its box centre, which is handy for placing next to a known object. Walk or
hover to where the object stands, take x and z, and size the box to cover it.

## Linking an object to an asset

Give the object a `tag` when it is one of the 30 builder-pack assets. The asset then moves to your object:

- Its data, diagnosis and route all follow the new position.
- The object that held the tag before keeps its place but loses the link, so one asset is never in two places.
- The mapping becomes `manual (data/objects)` with confidence 0.9, and counts as a confirmed position.
- A tag that is not in the builder pack, or given to two objects, stops the build with a message.

These 7 assets are on objects that do not look like their class, so their positions are unconfirmed. They are the
most useful ones to place by hand. Example 4 is the query that lists them:

| Tag | Current object | Condition |
|---|---|---|
| M-001 | `vlm_022` (other) | watch |
| M-002 | `cls_032` (tank) | healthy |
| M-003 | `cls_031` (tank) | watch |
| M-005 | `obj_001` (tank) | degraded |
| VS-001 | `vlm_033` (tank) | healthy |
| VS-002 | `obj_017` (electrical cabinet) | degraded |
| VS-003 | `vlm_019` (tank) | healthy |

## Where an object goes

```
data/objects/*.json  ──┐   checked by pipeline/added_objects.py
                       ├─> pipeline/build_scene.py ──> web/data/scene.json ──> the 3D page and the backend
data/semantic_layer.json ┘   (objects from the scan)        │
                                                             └─> pipeline/build_layer.py ──> data/semantic/
                                                                  (table asset_location)      the assistant's data
```

- `data/semantic_layer.json` holds the objects found in the scan. It is regenerated by the extraction, so do not
  edit it.
- `web/data/scene.json` is what the page loads. [Example 5](examples/05_scene_item.json) shows two items exactly as the
  page receives them: one linked to an asset, one not.
- `data/semantic/` is the data layer the assistant queries. The table `asset_location` holds where each asset sits
  and how it was placed.

## How the page shows it

| Object | In the page |
|---|---|
| Linked to an asset | A box coloured by condition (green healthy, amber watch, orange degraded, red attention required). It is listed under Nearby when the walker is close. Clicking it opens the diagnosis, and it can be a route target. |
| Not linked | A grey box labelled with its class. It is shown when **All boxes** is on or when you click it. Clicking it shows its details. |

Both can be routed to by id: type the id in the **To** field, or ask the assistant, for example "go to fire_ext_01".
Linked objects can also be reached by tag, type, area or data, for example "take me to the motor with the highest
bearing temperature".

## The data layer

The assistant never writes SQL. It fills in a query spec, and the backend checks every name against
`data/semantic/layer.yaml` before running it. [Example 4](examples/04_query_asset_location.json) is such a spec: it
lists unconfirmed positions together with each asset's condition, through the `state` join.

To teach the assistant something new about the data, such as a rule, a synonym or a join, edit
`data/semantic/knowledge.yaml` and rerun `build_layer.py`. Never edit `layer.yaml` or `plant.sqlite`: they are
regenerated, and the build stops if a join or the pack's dashboard figures do not hold.

## When something goes wrong

The checker and the build name the file, the object and the fix. The common ones:

| Message | Fix |
|---|---|
| `id ... is already used` | Pick an id no other object has. |
| `tag ... is not in the builder pack` | Use one of the 30 tags, or leave `tag` out. |
| `box.min must be below box.max` | Swap the values on the axis it names. Remember that y points down. |
| `unknown field(s)` | Check the spelling against the format table. |
| The box is in the wrong place | Check y: a box with a y above 1.167 is under the floor. |

Not supported yet: cut-out `.ply` files for added objects, and going to an unlinked object by its class, such as
"go to the drum". Use the id instead.
